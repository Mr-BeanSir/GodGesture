# Windows 输入与启动可靠性修复设计

日期: 2026-07-29

状态:已实施。本文保留根因、设计边界和设计时验收计划;当前实现与实际验证结果以
`docs/PROJECT_STATUS.md` 为准。实施时 Tauri 开发配置采用 CLI 内联 `--config` JSON
覆盖,不创建临时文件。

## 目标

本次修复解决两个独立的 Windows 运行时问题:

1. 用户释放未形成手势的右键后,Windows 原生右键菜单存在约 500 ms 到 1 秒的
   肉眼可感延迟。
2. Desktop 开发端口被占用时启动直接失败;完整 GodGesture 实例已运行时,再次
   启动开发版或构建产物缺少明确提示。

右键修复的完成标准是释放后立即出现原生菜单,而不只是最终能够出现。菜单坐标
稳定性是同一路径上的伴随正确性要求,不能代替延迟验收。

## 已确认实现差异与根因假设

### 右键点击恢复

GodGesture 必须先吞掉触发键按下,才能在后续移动中决定它是普通点击还是手势。
当前 tracker 在抬起时已经能立即判定普通点击,但 Windows 平台在原始低级鼠标钩子
回调尚未返回时同步调用 `SendInput`,嵌套注入完整的 down/up。这是当前代码中唯一
位于抬起判定与目标收到点击之间的特殊时序,也是 500 ms 到 1 秒延迟的首要根因
假设。当前 Windows 输入实现还丢弃了 tracker 传入的点击坐标,使延迟期间的光标
移动影响菜单位置。

WGestures 的对应实现只在低级钩子中完成吞放裁决并投递内部消息;钩子回调返回后,
消息循环才重放 down/up。这一差异是本次 Windows 修复的参考边界,不用于推导其他
GodGesture 产品行为。

### 开发端口与单实例

Desktop 当前同时配置了 Vite `strictPort: true` 和固定 Tauri
`devUrl=http://127.0.0.1:14200`。单独允许 Vite 自动换端口会使 Tauri 仍连接旧地址,
因此不能只删除 `strictPort`。端口选择必须在启动两者之前完成,并把同一结果传给
Vite、HMR 与 Tauri。

生产与开发运行时已经注册 Tauri single-instance 插件,但第二实例回调只显示并聚焦
既有窗口,没有明确的用户提示。

## 设计

### Windows 点击重放队列

保留平台无关 tracker 的按下待定和抬起判定语义。Windows 平台不再从低级钩子
回调内直接执行普通点击重放,而是向钩子线程的 Win32 消息队列投递带有按钮与坐标
的内部消息。当前钩子回调先返回;消息泵随后处理内部消息并立即调用 `SendInput`
重放 down/up。

队列所有权放在 Windows hook/platform 层,不把 Win32 消息概念泄漏进共享 tracker。
消息载荷使用进程内有界状态保存,Win32 消息只承担唤醒作用。连续请求保持 FIFO;
投递失败时记录结构化错误且不阻塞钩子线程。合成事件继续携带现有
`EXTRA_INFO_TAG`,保持钩子重入时 fail-open 的既有保护。

Windows 重放在需要时先定位到捕获的抬起坐标,发出 down/up 后不额外等待。由于用户
可能在内部消息执行前主动移动光标,实现不得在较晚时刻再次移动或长期覆盖用户的新
位置;坐标定位与重放处于同一短操作,重放后不执行延迟恢复。右键延迟的主要验收仍是
抬起到目标菜单出现的时间,不是坐标行为。

`SynthesizeDown` 的起始超时拖拽语义与普通完整点击不同,本次不擅自改为异步队列;
实现时通过测试保护其 down 与后续真实 up 的顺序。

macOS CGEventTap 的同步吞放与模拟事件路径保持不变。本次是显式 Windows 缺陷修复,
后续真实 Mac 验收继续按 `docs/qa/M4_MACOS_SMOKE.md` 执行。

### 动态开发端口

新增仓库内 Node 启动器作为 `dev:desktop` 的入口。启动器从首选端口对
`14200/14201` 开始,按连续端口对查找两个都可绑定到 `127.0.0.1` 的组合。找到后将
端口通过本次子进程环境变量传给 Vite 配置,并通过 CLI 内联 `--config` JSON 覆盖
Tauri `devUrl`;控制台打印最终的页面与 HMR 地址。

Vite 继续使用 `strictPort: true`,用于发现端口预检后的竞争占用。Tauri `devUrl`
通过启动器生成的 CLI 内联 `--config` JSON 覆盖,不修改已提交的生产配置,也不产生
需要清理的临时文件。端口被 Vite-only 会话或其他程序占用时自动换端口,不终止任何
现有 Node、Cargo 或其他进程。

若没有可用端口对,启动器输出明确错误和已检查范围后非零退出。

### 完整实例检测与提示

Tauri single-instance 插件继续作为开发版和构建产物的权威实例裁决。第二实例不得
进入应用 setup、安装钩子或占用开发资源。既有实例收到普通重复启动时:

- 显示并聚焦设置窗口;
- 通过 vue-i18n 的 `zh-CN`/`en` 文案显示“GodGesture 已在运行”提示;
- 记录重复启动事件,第二进程正常退出。

`--autostart` 重复触发只记录日志并退出,不显示窗口或提示,避免登录时打扰用户。
开发启动器不自行用进程名代替 single-instance 锁,以免误判不同构建或残留进程。
如果完整实例已经运行,Tauri 的实例裁决会明确通知已有实例并停止新实例;端口自动
切换只解决开发服务器端口冲突,不允许形成第二个完整 GodGesture 实例。

## 错误处理

- 内部点击消息投递失败不得卡住低级钩子;唤醒失败时回滚刚入队的请求并记录错误。
- `SendInput` 短写继续使用现有 best-effort up 恢复,避免遗留逻辑按下状态。
- 开发端口预检只检查回环绑定能力,不杀进程;竞争失败由 `strictPort` 明确报错。
- 单实例通知无法发送到 WebView 时,仍显示并聚焦既有窗口且记录警告。

## 验证

以下为设计时验收计划;实际执行结果和仍缺少的实机证据统一记录在
`docs/PROJECT_STATUS.md`。

自动验证计划:

- Windows hook 队列的 FIFO、回调返回后执行、投递失败和关闭清理测试;
- 普通点击重放的 down/up 顺序、模拟事件标记、短写恢复和坐标测试;
- tracker 点击/手势/起始超时既有测试保持通过;
- 动态端口选择测试覆盖首选端口可用、单端口占用、整对占用、范围耗尽和竞争失败;
- 单实例普通重复启动与 `--autostart` 分支测试,以及双语提示键测试;
- Desktop test/typecheck/build、Rust lib tests 与 clippy。

Windows 实机验证计划:

1. 在未启动 GodGesture 与修复后的真实 Tauri 会话中,分别对桌面、Explorer 和浏览器
   执行普通右键。记录抬起判定、内部消息处理和 `SendInput` 的高精度时间戳;调度应为
   毫秒级,且原生菜单无肉眼可感延迟。
2. 在抬起后立即移动鼠标,确认菜单不会因延迟到 500 ms 到 1 秒后才出现。
3. 保持 14200 被 Vite-only 会话占用,执行 `npm run dev:desktop`,确认自动选择下一组
   端口并成功连接 Tauri。
4. 已有完整开发实例时再次执行开发命令,确认既有窗口被聚焦并显示提示,且没有第二
   个引擎或钩子。对构建产物重复运行执行同样验证。
5. 通过 `--autostart` 模拟重复启动,确认静默退出且不抢焦点。

如果改为消息队列重放后仍可稳定观察到 500 ms 到 1 秒延迟,则该根因假设被否定。
后续诊断必须继续记录低级钩子回调返回、`SendInput` 完成和目标窗口收到右键消息的
时间,定位下一处等待点;不得用额外 sleep、缩短手势阈值或仅修复菜单坐标宣称完成。
